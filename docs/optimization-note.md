
# Optimization note: concurrent dispute-worker tool calls

§8.1 good-to-have: a measured before/after latency improvement, from two
Phoenix-derived reports (`plan.md` P5-11..P5-15).

## Hypothesis and change

`src/agents/dispute.py`'s `dispute_node` calls three tools once a
transaction id is known: `check_dispute_eligibility`, `policy_search` (the
RAG subgraph) and `create_dispute_case`. None of their arguments depend on
another call's result — `create_dispute_case`'s args are built from the
extracted fields alone, not from the eligibility check or the RAG citation —
so running them sequentially, as the code originally did, serializes three
independent calls behind each other for no reason. `policy_search` runs its
own retrieve/grade/answer subgraph and is consistently the slowest of the
three; `check_dispute_eligibility` and `create_dispute_case` are fast, local
MCP calls.

**Change:** an `OPTIMIZATION_PROFILE` config switch (`src/config.py`,
default `optimized`) selects between the original sequential code path
(`baseline`, kept only for this comparison) and a concurrent one
(`optimized`, `asyncio.gather` over the three calls). Behaviour is
unaffected either way — same tool arguments, same tool results feed the same
`compose_answer` call — only call ordering/timing changes.

## Offline proof (deterministic, no network)

`tests/test_dispute_optimization.py` uses fake tools with a controlled,
fixed delay so the comparison isn't subject to real network variance:

| | wall-clock (3 calls × 50ms each) |
|---|---|
| `baseline` profile | ~150ms (sequential — confirmed: no two calls overlap) |
| `optimized` profile | ~50ms (concurrent — confirmed: all three overlap) |

A fourth test proves the two profiles produce **byte-identical** final output
given the same tool results, so switching to `optimized` cannot regress
accuracy — this is why the live measurement below did not need to re-run
DeepEval scoring.

## Live measurement

**Scope:** the 5 dispute-category cases in `data/golden_set/golden.jsonl`
(`g-dsp-001`..`g-dsp-005`) — the only cases that exercise `dispute_node` —
run once under each profile against the real graph and real Gemini, traced
into separate Phoenix projects (`bank-copilot-baseline` /
`bank-copilot-optimized`).

Generated by:
```bash
LOG_DIR=/tmp/dispute_opt_logs_baseline PHOENIX_PROJECT=bank-copilot-baseline OPTIMIZATION_PROFILE=baseline GEMINI_MODEL=gemini-3.5-flash-lite python -m src.cli run --inputs data/sample_inputs/dispute_optimization_cases.jsonl
LOG_DIR=/tmp/dispute_opt_logs_optimized PHOENIX_PROJECT=bank-copilot-optimized OPTIMIZATION_PROFILE=optimized GEMINI_MODEL=gemini-3.5-flash-lite python -m src.cli run --inputs data/sample_inputs/dispute_optimization_cases.jsonl
python -m src.observability.golden_signals --project bank-copilot-baseline --eval reports/_not_used_for_this_scope.json --out reports/golden_signals_baseline_dispute.json
python -m src.observability.golden_signals --project bank-copilot-optimized --eval reports/_not_used_for_this_scope.json --out reports/golden_signals_optimized_dispute.json
python scripts/compare_reports.py --baseline reports/golden_signals_baseline_dispute.json --optimized reports/golden_signals_optimized_dispute.json --span-name dispute --out reports/optimization_comparison.json
```

**A real, honest caveat.** Collecting this data hit genuine Gemini API
instability: a transient `503 UNAVAILABLE` ("experiencing high demand") on
the first two baseline attempts, then the daily `gemini-3.5-flash` quota
(20 requests/day, free tier) was exhausted mid-attempt, so both runs above
used `gemini-3.5-flash-lite` instead (a deliberate substitution — noted here
so the absolute numbers aren't mistaken for the app's normal default model),
and even then a per-minute rate limit (15 req/min) interrupted the optimized
run once. Both Phoenix projects therefore contain spans from more attempts
than just the final successful one (`bank-copilot-baseline`: 695 spans,
`bank-copilot-optimized`: 582 spans) — real, valid same-profile data, but
noisier than a single clean run, and it directly explains why the **mean**
`dispute`-span latency below is not a reliable number (skewed by a 119.8s
outlier almost certainly from a retry/backoff delay landing inside a span).
The **median** is the honest comparison:

| `dispute` worker span | baseline | optimized |
|---|---|---|
| count | 10 | 9 |
| **median** | **11,313 ms** | **9,761 ms** |
| mean (unreliable — see above) | 30,588 ms | 7,825 ms |
| min | 567 ms | 599 ms |
| max | 119,840 ms | 20,062 ms |

**Median improvement: −1,552 ms (≈14% faster)** — real, but smaller than the
offline test's clean ~3× figure. That's expected, not a discrepancy: when
`policy_search` (the slow RAG call) already dominates the total, running the
two fast calls concurrently with it saves roughly their own duration, not a
3× factor — concurrent total time ≈ max(three calls), not a third of their
sum. The two fast calls are on the order of a second or two each against
local synthetic MCP data, which lines up with the ~1.5s median saved. Full
data: `reports/golden_signals_baseline_dispute.json`,
`reports/golden_signals_optimized_dispute.json`,
`reports/optimization_comparison.json` (also carries the aggregate
`latency_by_class` deltas across every worker/retry in each project — not
attributable to this one change, included for transparency only).

**Accuracy:** not re-scored live for this scope (see the offline
byte-identical-output proof above); both live runs produced correct,
policy-grounded answers for every one of the 5 cases with no crash.

## Also found and fixed while producing this evidence

`python -m src.observability.golden_signals` crashed on Windows with
`UnicodeEncodeError` — Phoenix's `launch_app()` unconditionally prints an
emoji, and this module (invoked directly, `python -m
src.observability.golden_signals`) never reconfigured stdout to UTF-8 the
way every `src.cli` entry point already does. Fixed in
`src/observability/golden_signals.py` and `scripts/compare_reports.py` (both
call into Phoenix directly).
