## 2. Design decisions and assumptions

| ID | Decision / assumption | Why |
|---|---|---|
| D-01 | `main` holds **one root commit only**; all other work arrives through six merge commits made from PRs on the remote | §5.2 NFR-07 ("≥3 PR-driven merges, no direct pushes to main"); §7.7 Git workflow |
| D-02 | Six **stacked** branches: `phase-N` is created from `phase-(N-1)` | Requested by the team; merges will be sequential |
| D-03 | Both teammates work on everything together, so **every commit credits both**: Git allows one author per commit, so one teammate is the author and the other is listed in a `Co-authored-by:` trailer. The default author alternates A/B (the human may override per commit); the helper also sets the committer to the author, so both people appear as author *and* committer across the history | Both teammates must be visible on every commit |
| D-04 | **`run_id`** = our own UUID generated per conversation run and stamped as a span attribute (`metadata.run_id`, and `session.id`) on every span, and written into `tool_calls.jsonl` and `agent_actions.jsonl`. Failure citations use `run_id` + `trace_id` + `span_id` | §5.1 AC-08 and §8 ask for "Phoenix run_id + span_id"; Phoenix natively exposes `trace_id` and `span_id` |
| D-05 | Span-type mapping for golden signals: **thinking** = LLM spans; **tool** = TOOL + RETRIEVER spans; **acting** = AGENT/CHAIN (graph-node orchestration) spans excluding their LLM/TOOL children. Mapping lives in `src/observability/span_types.py` and is documented in the README | §7.3, §8 (Golden-signals report: "split by span type (thinking / acting / tool)") |
| D-06 | **Evidence policy:** from P3 on, runs append to `logs/*.jsonl` (append-only, real history including failing runs). Tests and throwaway experiments set `LOG_DIR` to a temp dir. The `regenerate` command writes to gitignored `artifacts_regen/` by default and only overwrites committed evidence with `--commit-evidence` | Keeps cited `run_id/span_id` values stable; still satisfies NFR-02 |
| D-07 | Phoenix runs **locally in-process** (UI on `localhost:6006`); its working directory `.phoenix/` is persisted across runs (gitignored) so the final export contains all runs, including failure runs | §4 Observability, §8 |
| D-08 | Windows-friendly: pure-Python CLI (`python -m src.cli …`), `pathlib`, no Makefile. Git helper uses bash → run it in Git Bash | Team laptops appear to be Windows |
| D-09 | Only the §4 approved tools plus **supporting libraries they require** (e.g. `langchain-google-genai`, `pydantic`, `pandas`, `pyarrow`, `aiosqlite`, `httpx`, `uvicorn`, `pytest-asyncio`, `spacy` model for Presidio). No Faker, no other agent frameworks, no other LLM SDKs | §4 "fixed open-source toolchain" |
| D-10 | PAN/account numbers are masked at the **earliest boundary** (CLI ingress) so LLM prompts, Phoenix spans and logs only ever see masked values | §3.4 Synthetic-Data Rule, NFR-05 |
| D-11 | Tests that need real Gemini calls are marked `@pytest.mark.live`; default `pytest -m "not live"` is offline (fake LLMs) | Speed, quota, determinism |
| D-12 | Governance docs cite controls through a **control catalog** (`docs/control-catalog.md`, IDs `CTL-01…`) whose entries point at real files/functions; a script verifies every citation resolves | §3.4 Citation-Resolves Rule; §7.5 "citation-gated" |
| D-13 | The copilot **never commits money movement**: refunds/dispute outcomes are *drafts for a human agent* | §5.1 AC-02; output-risk gating (§7.5) |
| D-14 | The synthetic-PAN "before" sample in the PII-redaction report is allowed to contain an obviously synthetic PAN (the report exists to show redaction); the evidence PII scanner allow-lists exactly that file | §8.1 requires a before/after sample; see Open question Q-4 |

### 4.3 Commit message convention (graded — follow exactly)
```
<type>(<scope>): <imperative subject, ≤72 chars, no trailing period>

<body: WHAT changed and WHY, wrapped at 72 chars. Mention design choices,
 library versions used if relevant, and how it was verified.>

Refs: <requirement IDs and ref-doc sections, e.g. AC-07, NFR-06, §7.2>
Evidence: <path>                     # only on evidence commits
Generated-by: <exact command run>    # only on evidence commits
Co-authored-by: <the OTHER teammate> <email>
```
- **Types:** `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `chore`, `build`, `data`.
- **Scopes:** `repo, config, common, data, mcp, llm, graph, agents, tools, cli, rag, context, memory, observability, guardrails, security, evaluation, verify, api, governance, arch, perf, failure, evidence, readme, deps, delivery, release`.
- Every commit body explains **what and why**. Evidence commits always have `Evidence:` + `Generated-by:`. The `Co-authored-by:` trailer is **always the last line** and there is no blank line between `Refs:` and the trailers (so Git parses them as trailers).
- One logical change per commit. **Never** mix code and the evidence it generates in the same commit unless the code is tiny; code first, evidence after.
- Never put keys, real names, real numbers, or full PAN/account numbers in a commit message.

### 4.4 Authorship rule (both teammates on every commit)
- **Both teammates work on this project together, so every commit credits both:** one is the **author**, the other is the **co-author** (`Co-authored-by:` trailer). Nothing is ever credited to only one person.
- The letter after each commit ID (A or B) is only the **default author**; the defaults alternate A, B, A, B … so both teammates also appear as the *author* of roughly half the commits. If the human tells you who actually wrote a given commit (or that they paired on it), use that person as the author for that commit; the other person is still the co-author. Do not ask again per commit — follow the default unless told otherwise.
- The helper (Appendix B) sets `GIT_AUTHOR_*` and `GIT_COMMITTER_*` to the listed author and appends `Co-authored-by:` for the other teammate — so both people appear on every commit.
- Verification (run at the end of every phase):
  ```bash
  # every commit in the phase has a co-author trailer
  ```

## 14. Known gotchas

1. **DeepEval defaults to OpenAI** — always pass the custom Gemini judge; set telemetry opt-out; no `OPENAI_API_KEY` anywhere.
2. **Check installed APIs** of Phoenix (`launch_app`, spans dataframe client), openinference LangChain instrumentor, LangMem, langchain-mcp-adapters (client construction/context-manager semantics differ across versions), LangGraph prebuilt agents (may have moved to LangChain's newer agent helpers), and the SQLite store/checkpointer modules. Pin what actually works.
3. **First-run downloads** (personal laptop only): Sentence-Transformers model, spaCy model for Presidio, any LLM Guard models. Document in README.
4. **Gemini rate limits:** use exponential backoff with jitter, modest concurrency, a Flash-tier judge, and `--limit` smoke runs.
5. **MCP stdio:** the server must never write to stdout except protocol frames; log to files only.
6. **Windows:** run the Git helper in Git Bash; use `python -m …`; avoid shell-only tooling in required flows; mind `asyncio` event-loop policy.
7. **Phoenix persistence:** keep `.phoenix/` until the P5 export is committed; do not delete it during development.
8. **Evidence honesty:** failure analysis and metrics come from real runs; never edit generated files by hand.
9. **Regeneration overwrites ids:** re-running with `--commit-evidence` changes span ids, which would break `docs/failure-analysis.md` citations; only use it before the failure analysis is written (P3/P4) or re-run `verify_citations.py` immediately afterwards.
10. **Stacked branches:** if you fix something in an earlier phase after later branches exist, do **not** rebase; add a corrective commit on the current branch instead.

## Appendix B — Commit helper (keep OUTSIDE the repo; run in Git Bash; do not commit)

```bash
# ~/hackathon_git_helpers.sh    →   source ~/hackathon_git_helpers.sh
export NAME_A="[NAME_A]"  EMAIL_A="[EMAIL_A]"
export NAME_B="[NAME_B]"  EMAIL_B="[EMAIL_B]"

# usage: gc <A|B> "<subject>" "<body>" "<trailer lines>"
#   trailer lines = Refs: …  (and, on evidence commits, Evidence: … / Generated-by: …), newline separated
gc() {
  local who="$1" subject="$2" body="$3" trailers="$4"
  local an ae cn ce
  if   [ "$who" = "A" ]; then an="$NAME_A"; ae="$EMAIL_A"; cn="$NAME_B"; ce="$EMAIL_B"
  elif [ "$who" = "B" ]; then an="$NAME_B"; ae="$EMAIL_B"; cn="$NAME_A"; ce="$EMAIL_A"
  else echo "first argument must be A or B" >&2; return 1; fi
  {
    printf '%s\n\n' "$subject"
    printf '%s\n\n' "$body"
    printf '%s\n' "$trailers"
    printf 'Co-authored-by: %s <%s>\n' "$cn" "$ce"
  } | GIT_AUTHOR_NAME="$an"  GIT_AUTHOR_EMAIL="$ae" \
      GIT_COMMITTER_NAME="$an" GIT_COMMITTER_EMAIL="$ae" \
      git commit -F -
}

# example (P1-02, author B):
git add src/config.py .env.example
gc B "feat(config): add env-var config loader and .env.example" \
"src/config.py reads GOOGLE_API_KEY, GEMINI_MODEL, LOG_DIR and PHOENIX_*
settings through python-dotenv with safe defaults. .env.example lists
every variable with placeholder values only; .env stays gitignored." \
$'Refs: NFR-01, §7.4 Secrets hygiene, §4 Security (python-dotenv)'

# example evidence commit (P1-20, author B):
git add logs/mcp_transcript.jsonl
gc B "chore(evidence): record MCP transcript from sample conversations" \
"Ran the MCP demo so the transcript contains real tool calls and the
resource read; tool names match mcp_server/server.py; no PAN/account
number appears in plaintext." \
$'Evidence: logs/mcp_transcript.jsonl\nGenerated-by: python -m src.cli mcp-demo\nRefs: §7.1 MCP server, §8, NFR-05, NFR-06'

# inspect the last commit
git log -1 --format='%an <%ae> | %cn <%ce>%n%B'
```
